# 建立 Merge Request

依下列步驟進行。**每個產生對外副作用的動作前，都必須先讓使用者確認。**

## 1. 從上方狀態推導出已知資訊

不要重跑指令，直接從「目前狀態」區塊讀出這兩項：

- **專案位置**：Remote URL 套 `<git-host>[:/]([^/]+)/([^/]+?)(?:\.git)?$`，取出 `{group}` / `{repo}`
- **候選單號**：分支名開頭套 `^([a-zA-Z]+-\d+)` 並轉大寫（`proj-1780-fix-login` → `PROJ-1780`）；
  若叫用時帶了 `$1`，以 `$1` 優先

任一項推不出來就留空，**不要猜**——下一步會問。

## 2. 一次問清楚三件事

合併成單次提問，不要逐題往返：

| 要問的 | 怎麼問 |
|---|---|
| 來源分支 | 顯示上方偵測到的分支，請對方確認或改寫 |
| 目標分支 | 直接詢問 |
| 工作單號 | 有候選 → 確認 / 改寫 / 回「無」；無候選 → 詢問，沒有請回「無」 |

## 3. 補齊工作單資訊（若有單號）

用工作管理平台的 API 以自訂 ID 查詢，取得標題與完整連結。

**查詢失敗時照常繼續**，後續省略連結即可，不要中斷流程。

## 4. 讀出這批變更做了什麼

```bash
git log {目標分支}..HEAD --oneline
git diff {目標分支}...HEAD --stat
```

> diff 用**三個點** `...`（相對於分岔點），不是兩個點——否則目標分支的新 commit 會混進來。

## 5. 組出標題與內文

**標題**：`{單號} {簡短描述}`，無單號時只留描述。
不要加 Conventional Commits 前綴（`feat:` / `fix:`），那是 commit 的規範。

**內文**：

```markdown
## 這個 MR 做了什麼

- {依 commit 與 diff 條列，說明改了什麼、為什麼}

## 相關連結

- 工作單：{單號}
```

無單號時整段「相關連結」省略。

## 6. 預覽並修改

把草稿完整呈現，詢問：「以上是否需要調整？請直接說明修改意見，或回覆確認。」

**反覆修改直到使用者明確確認為止。** 未確認不得進入下一步。

## 7. 推送分支

若上方推送狀態顯示尚未推送或落後：

```bash
git push -u origin {目前分支}
```

## 8. 建立 MR

```bash
glab mr create \
  --title "{最終標題}" \
  --description "{最終內文}" \
  --target-branch {目標分支} \
  --hostname <git-host>
```

目標分支為 `main` / `master` 時額外加上 `--remove-source-branch`。

完成後把 MR 連結顯示給使用者。

## 9. 發送通知（詢問後才做）

先問：「是否發送審核通知到 `<通知目標>`？」

<!-- ⚠️ 以下整塊由 /onboard 依團隊實際使用的通訊平台改寫，不是替換幾個尖括號就好。
     訊息語法、跳脫規則、目標識別方式各平台都不同，必須整段重寫。 -->

同意的話依下列格式組合訊息：

```
<依平台語法組出的訊息模板。要包含：MR 標題與連結、repo、來源分支 → 目標分支、
 工作單連結（若有）、變更摘要條列>
```

平台注意事項：

- **連結語法**：`<該平台的連結寫法>`
- **Emoji**：`<直接用 Unicode／需要特殊處理／不支援>`
- **特殊字元**：`<需要跳脫的字元與規則，沒有就寫「無」>`
- **長度限制**：`<單則訊息上限，超過要怎麼處理>`
- 無工作單號時整行「工作單」省略

**呈現訊息預覽並標註發送目標，使用者確認後才呼叫 API。**

發送目標：`<通知目標>`（API 呼叫時使用 `<目標 ID>`——見團隊 `CLAUDE.md` 的對照表）

## 貫穿全程的規則

以下規則在整個流程中持續有效，不是一次性的檢查：

- 步驟 6、9 兩個確認點**不可略過**。即使使用者說「都照你的」，也要把最終內容顯示出來再送
- 任何一步失敗就停下來回報，不要自行嘗試替代方案
- 不要修改任何程式碼檔案——這個 skill 只負責發布流程
