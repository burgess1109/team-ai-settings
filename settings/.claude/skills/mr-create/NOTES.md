# mr-create — 設計說明

> 給維護者看的，**不要從 `SKILL.md` 連結這個檔案**。
> 沒有被連結的檔案不會被讀取，所以這些說明完全不佔 context。

## 幾個設計決定

**1. 開頭的 `` !`command` `` 動態注入**

這些指令會在 Claude 看到內容**之前**先執行，輸出直接嵌進 prompt。
所以「取得 git 資訊」不需要額外一輪 tool call，skill 一載入狀態就已經在眼前。

**2. `disable-model-invocation: true`**

沒有人會用講的說「幫我建 MR」，關掉 AI 自動叫用零損失，
而且這個設定會讓 description 完全不進 context——連那一行都不用付。

也因為如此，description 是寫給**人**看的（出現在 `/` 選單），
不需要 `Triggers:` 關鍵字清單——Claude 根本讀不到那段字。

> 如果團隊實際上會說「幫我開個 MR」，那就該拿掉這個欄位並補上 triggers。
> 兩者互斥，見 `create-tag/NOTES.md` 的對照表。

**3. `allowed-tools` 只放 `Bash(git *)` 與 `Bash(glab *)`**

不要開整個 `Bash`——那等於此 skill 執行期間任何指令都免確認。
注意這個欄位是**預先核准**不是限制：沒列出來的工具照樣可用，只是會照常要求確認。
要納入 MCP 工具時在此列出對應的工具名稱。

**4.「貫穿全程的規則」放最後，不寫進步驟裡**

skill 內容載入後會常駐整個 session，且 Claude 不會重讀檔案。
寫進編號步驟裡的規則，流程走到後半段時讀起來像「已完成的一步」；
寫成常駐約束才會持續生效。

## 可以再拆的地方

步驟 9 的平台訊息格式規則（連結角括號、emoji、mention 語法）只有走到最後才需要，
主檔長大時可以抽到 `reference.md`，並在 `SKILL.md` 用一句話指路。
現在只有 160 行左右，還不必要——官方的建議線是 500 行。
